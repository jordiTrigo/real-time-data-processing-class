the contract

A fluent answer is not an incident response.

Observe

Every conclusion cites a metric, query, log line, trace, or record identity.

Authorize

Correctness does not grant permission. State-changing actions wait for a human.

Verify

Green containers are supporting evidence. Recovery includes an expected signal and canary proof.

Harden

Every failure becomes a monitor, contract test, capacity limit, runbook, or eval case.

the incident loop

Diagnosis is a sequence of better questions.

symptom→steady state→hypotheses→least-invasive observation→evidence
root cause→propose action→human approval→fix→verify→harden
Rule: “I checked the logs” is not evidence. Record which log, line, metric, query, time window, order id, LSN, partition, offset, or schema version changed your mind.

CTF rules

Fixing the symptom is not finishing the incident.

1 · Record

Start the post-mortem timeline and evidence ledger while investigating.

2 · Compete

Write at least two plausible causes before editing a config.

3 · Minimize

Ask for the smallest read-only observation that eliminates one cause.

4 · Propose

State scope, risk, rollback, and expected recovery signal before changing state.

Finish condition: root cause + exact evidence + safe fix + prevention + a verified canary. A green dashboard alone does not close the incident.
field guide

The first discriminating observation.

Probe retries

Match repeated offset and schema ID to the Registry lookup.

Partition skew

Compare broker end offsets and inspect the stable record key.

Source risk

Compare current and confirmed slot LSN; inspect the connector task.

Business wrong

Compare source outliers, downstream totals, and the unchanged schema.

Parts jump

Inspect active parts, merges, and recent insert sizes.

Retention risk

Inspect time/byte policy, then calculate capacity before an outage.

Two traps: an idle source makes freshness age without a failure; schema-valid data can still be semantically wrong.

agents versus workflows

Use judgment where ambiguity exists.
Make everything else boring.

Deterministic workflow

baseline → run verifier → record result → alert/stop

repeatable · cheap · testable

Bounded agent judgment

given symptom + evidence, select the next read-only inspector and explain why

uncertain · constrained · observable

Teacher beat: “An agent is not a workflow with a more expensive `if` statement.”
tools are APIs

Give a model a narrow instrument panel.

# never the default
run_shell(command: str) -> str
get_partition_lag(topic) -> PartitionLag[]
get_connector_status(name) -> Status
get_slot_status(slot) -> Slot
get_parts_stats(table) -> Parts
get_schema_versions(subject) -> Schema[]
Tool quality is agent quality: descriptions, typed parameters, result shape, errors, and permission level are part of your application design.
MCP

A reusable boundary for capabilities and context.

Tools

inspect lag, query parts, read connector status; actions only with scoped approval.

Resources

pipeline topology, schema history, runbooks, prior post-mortems.

Prompts

“Investigate stale orders” with the right evidence ledger and constraints.

MCP is not permission magic. A reusable tool still needs least privilege, auditability, and an approval boundary.

multi-agent, briefly and skeptically

Four agents—or one agent with four good tools?

Investigator

read-only evidence collection

Streaming specialist

lag, partitions, checkpoint

Database specialist

slot, parts, query pressure

Controller

proposal and approval only

Default verdict: start with one stateful investigator and typed tools. Add specialists only when evals show distinct context or authority improves safety/correctness.

close

An agent is a distributed system.

Its events are messages and tool calls. Its state is context. Its checkpoints are memory. Its data-quality failures are unsupported claims.

Submit: one evidence-backed post-mortem + one safe agent vertical slice: tools, state, approval boundary, trace, and eval case.
