predice · el crash

Spark escribe un batch, y luego muere.

Escribe un batch en ClickHouse, y luego muere antes de hacer checkpoint. ¿Qué pasa?

✓
El batch se reproduce (replay). Spark reinicia desde el último checkpoint, que nunca avanzó, y vuelve a leer los mismos offsets de Kafka. ClickHouse gana filas duplicadas físicamente — el mismo order_id y el mismo LSN, escritos dos veces. La respuesta de la API no cambia — las filas duplicadas comparten versión, así que un colapso al momento de leer las trata como una sola.
lo que demuestra hoy

La atomicidad termina en la frontera del sistema.

Postgres confirma. Kafka confirma. Spark hace checkpoint. ClickHouse hace merge. Ninguno de esos cuatro commits es el mismo commit.

entonces, qué ES cierto

Estado actual effectively-once.

lesson11.orders_current
CREATE TABLE lesson11.orders_current ( order_id UInt64, customer_id UInt32, amount Decimal(10, 2), status LowCardinality(String), -- L10: 213.5x compression created_at DateTime64(3, 'UTC'), updated_at DateTime64(3, 'UTC'), version UInt64, -- Debezium source.lsn _is_deleted UInt8, source_topic LowCardinality(String), -- event identity, L6 kafka_partition UInt16, kafka_offset UInt64, source_ts DateTime64(3, 'UTC'), ingested_at DateTime64(3, 'UTC') DEFAULT now64(3) ) ENGINE = ReplacingMergeTree(version) PARTITION BY modulo(order_id, 16) ORDER BY order_id;
ⓘ
FINAL colapsa cada versión al momento de la consulta; gana el version más alto. Un delete no es un borrado físico — es una fila con un LSN más alto y _is_deleted=1 que gana ese mismo colapso.
!
Esto no es una transacción distribuida. Ningún commit de dos fases abarca Postgres, Kafka, Spark y ClickHouse. Es convergencia: dado tiempo suficiente, cada lector ve el mismo estado actual.

el formato en el cable

Cinco bytes antes de que empiecen los datos.

BYTE 0 magic byte 0x00 BYTES 1–4 schema ID big-endian, 4-byte integer BYTES 5+ payload Avro-encoded record
ⓘ
El schema ID viaja en cada mensaje — un consumidor nunca tiene que adivinar qué esquema escribió un registro.
la trampa

“El más reciente” es mentira para registros viejos.

!
Un topic retenido contiene registros escritos bajo cada versión de esquema que haya existido. Traer el esquema más reciente una vez y aplicarlo a todo el batch corrompe en silencio los registros viejos.
consumer — schema ID por registro
# the schema ID is inline on every record (bytes 1-4) — use it by_schema_id = defaultdict(list) for record in batch: schema_id = decode_schema_id(record.value) by_schema_id[schema_id].append(record) for schema_id, records in by_schema_id.items(): writer_schema = registry.get_schema(schema_id) normalized = [normalize(r, writer_schema, reader_schema) for r in records] union_batch.extend(normalized)

salto ③ · kafka

Un offset identifica un evento, no un pedido.

CampoQué te dice
keyla clave primaria del pedido — lo enruta a una partición
valueel sobre CDC codificado en Avro (before/after/source)
partitionuna de 3 — cdc.public.orders tiene 3 particiones
offsetla posición de este evento solo dentro de su partición
schema IDel ID de la registry de Confluent codificado en los primeros 5 bytes del value
!
El offset no ordena nada entre particiones. Con 3 particiones, los eventos de dos pedidos distintos pueden caer en particiones distintas sin relación alguna entre sus offsets. El offset identifica un evento dentro de su propia partición; no es un número de secuencia global para el estado actual.
salto ④ · spark

Los offsets del checkpoint no son offsets de consumer-group.

Spark rastrea su propio progreso de lectura. La API de consumer-group de Kafka nunca lo ve.

!
Estos offsets viven en el checkpoint de Spark, en un volumen persistente — NO son commits de consumer-group de Kafka. Esa es la razón entera por la que la métrica del dashboard se llama offset-head distance y no consumer lag: una herramienta estándar de lag de Kafka consulta offsets de consumer-group, y esta pipeline nunca escribe ninguno.

Por qué el checkpoint tiene que estar en un volumen persistente, no en /tmp: si lo pierdes, Spark no tiene memoria de lo que ya procesó.

salto ⑤ · clickhouse

Filas crudas vs. FINAL

sin FINAL

clickhouse-client
SELECT * FROM lesson11.orders_current WHERE order_id = :id;

Puede devolver varias filas físicas — una por cada versión que aún no se fusionó.

con FINAL

clickhouse-client
SELECT * FROM lesson11.orders_current FINAL WHERE order_id = :id;

Fusiona versiones al momento de leer. Una fila: la de mayor version.

ⓘ
Si esa fila ganadora es un marcador de delete, FINAL igual la devuelve — solo fusiona duplicados, no sabe que "delete" es especial. La API es la capa que lee el marcador y lo convierte en un 404.

expand / contract

Solo hicimos la mitad expand.

  • Lo que acabas de correr es expand: añadir, aditivo, backward-compatible, seguro de ejecutar bajo carga en vivo.
  • Contract — quitar el campo viejo, forzar a cada consumidor a dejarlo — está deliberadamente fuera de alcance hoy.
!
Contract es donde viven los outages. Quitar algo significa demostrar que cada consumidor ya dejó de depender de ello — eso es un problema de coordinación y rollback, no un mecanismo de schema registry, y es una migración de producción real, no una demo de lección.

lo que deberías ver realmente

La recuperación necesita tasa de drenaje > tasa de llegada.

  • la llegada sube por encima del throughput procesado

  • el freshness envejece
!
